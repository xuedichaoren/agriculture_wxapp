# 09 · 农户被认养与农事天气

这一篇记录两件事：**农户端认养方向的反转**，以及**天气预报的接入方式**。

---

## 1. 先修正一个方向性错误

原来的农户端是错的。第二个 tab「我的地」指向 `pages/farm/my` —— 那是**买家**的「我的认养」页；工作台里还挂着「认养新地块」按钮。

也就是说，农户登录后被引导去**认养别人的地**，而他自己家的地根本没地方发布。

这不是文案问题，是整个数据模型站在了买方一侧。修正后的分工：

| | 买家 | 农户 |
|---|---|---|
| 核心动作 | 认养一块地 | 把地放出来给人认养 |
| 关注 | 我的地长成什么样 | 这块地被谁认了、还有几个名额、这个月收了多少钱 |
| 入口 | 认养大厅 → 我的认养 | 我的地 → 被认养管理 |
| 数据 | `ADOPT_PLOTS`（平台的招募池） | `MY_PLOTS`（我自己的地块） |

两个模型刻意不共用：平台视角的地块字段是「还剩几份、口碑如何」，农户视角的字段是「我几个人手、每份多少钱、谁来履约」。

## 2. 农户侧的数据模型

文件：`api/farm-side.js`（种子数据 + 纯函数）、`store/farm-side.js`（所有会变的状态）

### 2.1 我的地块 `MY_PLOTS`

| 字段 | 说明 |
|---|---|
| `id` / `code` | `mp1` / `A-03`，code 是对外展示的地块编号 |
| `name` | 认得出的小名，如「阳坡辣椒地」 |
| `area` / `rows` | 面积（㎡）/ 垄数 |
| `crops` | 可种作物 id 数组，取自 `ADOPT_CROPS` |
| `price` / `marketPrice` | 认养单价 / 划线价 |
| `capacity` | **认养名额**，这块地能同时接几个人 |
| `status` | `recruiting` / `full` / `paused` / `draft` |
| `soil` / `sun` / `water` / `altitude` | 地块条件，买家决策依据 |
| `plantDate` / `harvestDate` / `yieldExpect` | 生产周期与预期产量 |

> `booked`（已认养份数）**不存在字段里**，由 `ADOPT_INS` 实时数出来。
> 存一个数字再手动加减，迟早和订单表对不上。

### 2.2 被认养订单 `ADOPT_INS`

```
{ id, plotId, code,
  adopter: { name, avatar, phone, city },
  crops[], planKey, cycleKey,
  startDate, endDate, amount,
  status: active | ending | ended | refund,
  freq, deliveriesTotal, deliveriesDone,
  remark, createdAt }
```

共 15 条种子数据（13 条在养 + 2 条已结束），覆盖 5 块地：

| 地块 | 名额 | 在养 | 状态 |
|---|---|---|---|
| A-03 阳坡辣椒地 | 6 | 4 | 招募中 |
| A-07 平地叶菜块 | 4 | 4 | 已满员（自动判定） |
| B-01 试验小垄 | 3 | 1 | 招募中 |
| C-02 高山黄桃树 | 4 | 2 | 招募中 |
| D-01 江边橙园 | 4 | 2 | 已下架 |

### 2.3 认养申请 `IN_APPS`

买家在大厅点「申请认养」不直接成单 —— 地块在农户手上，得他点头。

```
{ id, plotId, code, adopter, crops[], planKey, cycleKey,
  wantStart, months, amount, message, createdAt, status: pending }
```

`status` 不写回 `IN_APPS`，而是记在 `farmSide.apps[appId]`。种子数据保持只读，本地状态叠在上面，这样才能一键重置回演示态。

**为什么必须有这一步**：果树类一棵树只能挂一个人，多人同时付款会直接冲突。让农户按排产决定接不接，比系统替他拒绝要好。

## 3. 状态机

### 3.1 申请

```
pending ──通过──▶ accepted ──生成──▶ ADOPT_INS(active)
   └────婉拒──▶ rejected（可带原因，买家能看到）
```

`acceptApp(app)` 做的事：写状态 + 生成一张在养订单 + 名额立即占用。
重复调用返回 `null`，防止连点生成两张单。

### 3.2 地块状态

```
recruiting ──名额满──▶ full（自动）
     │                    │
     └──手动暂停──▶ paused ◀┘
```

`full` **不是**手填的状态，是 `booked >= capacity` 算出来的：

```js
export function effStatus(plot) {
  const ov = farmSide.plots[plot.id] || {}
  if (ov.status === 'paused') return 'paused'      // 暂停优先
  const booked = insOf(plot.id).length
  const cap = Number(ov.capacity || plot.capacity || 0)
  if (cap > 0 && booked >= cap) return 'full'      // 满了自动停
  return ov.status === 'draft' ? 'draft' : 'recruiting'
}
```

暂停招募不影响已有认养人履约，只在认养大厅里下架。

### 3.3 超额的处理

农户接单时如果名额已满，**不硬拦**，只提示：

> 这块地名额已满（4/4），仍可接单，但会出现超额。确认要接吗？

理由同上：农户知道自己的地能不能塞下第五个人，系统不该替他判断。页面上标出来就够了。

## 4. 收入怎么算

认养是一季度/半年一次性收的钱，直接摊在"本月收入"里会虚高。所以按合同期分摊：

```js
function monthlyOf(item) {
  const months = Math.max(1, Math.round((new Date(item.endDate) - new Date(item.startDate)) / 86400000 / 30))
  return Math.round(Number(item.amount || 0) / months)
}
```

例：￥537 认养 3 个月 → 本月记 ￥179。

`farmStats()` 的 `monthIncome` = 所有 `active` / `ending` 单的 `monthly` 之和。
`totalIncome` = 所有非退养单的合同金额之和。

后端有账期流水后，把这两处换成查询即可，页面不用动。

## 5. 打通往买家侧的闭环

改之前有个致命断点：**农户发布的地块只在农户端可见，认养大厅看不到，买家就算认了也打不开详情**。

### 5.1 依赖方向

让 `api/adopt.js` 引用 `api/farm-side.js`，但**反向不行**：

```
adopt.js ──▶ farm-side.js ──▶ mock/index.js
```

`api/farm-side.js` 原本从 `adopt.js` 借 `findCrop / planOf / cycleOf`，这会造成两个文件互相 import。ES 模块遇到环时，`const` 数组在模块求值期可能是 `undefined`，表现为「大厅空白」这种很难查的问题。

所以把这三个小查询在 `farm-side.js` 里本地实现一份（只依赖 `mock`），并把依赖方向用注释钉死。

### 5.2 合并点

```js
// adopt.js
function farmSidePlots() {
  // MY_PLOTS + localStorage 里本次会话新发布的地块
  // 补上 farmName / leftCount / adoptedCount，让它们长得像 ADOPT_PLOTS
}

export function findPlot(plotId) {
  return ADOPT_PLOTS.find(...) || farmSidePlots().find(...) || null
}

export function listPlots(filter) {
  // 平台地块 + 农户招募中且还有名额的地块
}
```

`plotView()` 里补一个兜底：农户地块没有 `farmId` 对应的农场记录，用 `farmName` 合成一个虚农场对象，详情页才能正常显示"湘西老周家庭农场"。

**效果**：农户发布 → 大厅可见 → 点进详情 → 下单 → 买家「我的认养」里也查得到（因为 `findPlot` 通了）。

> `farmSidePlots()` 里读了一次 `nh_farmside_v1`，这是为本地演示取的巧。
> 接后端后整段删掉，换成 `GET /plots/:id`。

## 7. 天气预报

文件：`api/weather.js`

### 7.1 四档 provider

| provider | 是否要 key | 说明 |
|---|---|---|
| `seniverse` | 需要 | **默认**。心知天气，国内数据源，乡镇级定位准、中文文案细 |
| `open-meteo` | 不需要 | ECMWF/GFS，7 日预报，作为心知失败时的自动兜底 |
| `qweather` | 需要 | 和风天气，国内节点快 |
| `mock` | — | 全部失败时落到这里，用日期做种子生成稳定假数据 |

切换方式：

```js
import { setWeatherConfig } from '@/api/weather.js'

// 换和风天气
setWeatherConfig({ provider: 'qweather', qweatherKey: '你的key' })

// 固定位置（不调定位）
setWeatherConfig({ useLocation: false, place: '湖南 · 湘西龙山', lat: 29.4528, lon: 109.4439 })
```

`setWeatherConfig` 改动 `provider / key / 坐标 / 天数 / proxy` 任一项都会清缓存，避免换源后还返回上一个源的数据。

### 7.2 心知天气接入要点

配置在 `weatherConfig`：

```js
{
  provider: 'seniverse',
  key: 'SppuqZrtfC9I215nM',        // 私钥
  publicKey: 'PVWO5-i0uW7Pp_gwQ',  // 公钥，端上不参与请求
  days: 3
}
```

**坑一：`key` 参数要传私钥，不是公钥。** 心知的密钥对里，「公钥」是身份标识，「私钥」才是 API key。传公钥会返回 `AP010003 The API key is invalid.`——看起来像 key 没激活，其实是传反了。

**坑二：免费版不支持公钥签名认证。** 官方文档推荐 `public_key + ts + ttl + sig` 的 HMAC-SHA1 签名方式，但实测免费版返回 `AP010004 The signature is invalid.`，试过 `public_key` / `uid` / `key` 三种参数名、带不带 `ttl`、sig 编不编码，全部同样报错。所以端上只能走 `?key=私钥` 直连。

> ⚠️ 这意味着私钥会跟着小程序代码包一起发出去。上线前必须把 `weatherConfig.proxy` 配成自己的服务端地址，请求只发坐标，key 留在服务端。`fromProxy()` 已经写好，返回结构对齐 `{ source?, now, days }` 即可。

**坑三：`precip` 是 0~1 的比值，不是百分数也不是毫米。** 实测广州小雨 `precip=0.37`、上海阴天 `precip=0.49`、龙山小雨 `precip=0.98`。按百分数读会得到「小雨 1%」这种自相矛盾的结论，进而让打药指数从 25 变成 80。用 `probPct()` 换算，`>1` 才按百分数兜底。

**坑四：码值表不可信。** 心知现象码有 100 个值，不同版本文档对不上（实测 `4=多云、9=阴、13=小雨`）。所以不硬编码码表，用接口返回的中文 `text` 做关键词映射（`seniverseText()`），码值只兜底。

免费版能力边界：

| 接口 | 返回 | 缺什么 |
|---|---|---|
| `now.json` | text / code / temperature | 湿度、风、降水、体感都没有 |
| `daily.json` | 3 天，含 high/low/precip/rainfall/wind_speed/humidity | 日出日落、紫外线没有 |

补齐方式：

- 湿度 / 风 / 降水 → 取 `daily[0]`
- 体感 → 温度 + 湿度 + 风速按经验公式折算（`feelsLike()`）
- 日出日落 → 本地用 NOAA 简化算法算（`sunTimes()`），带均时差修正，龙山 11 月中旬算出 07:10 / 17:46，与实际吻合
- 风速 → 心知给 km/h，全项目统一 m/s，除以 3.6

定位用坐标调用（`location=纬度:经度`），心知自己反查地名。实测 `29.45:109.44` 落到「龙山, 湘西, 湖南」，正是农场所在地，比按城市名猜可靠。

**小程序后台必须加 request 合法域名**：

```
https://api.seniverse.com      （心知天气，默认）
https://api.open-meteo.com     （兜底用，建议一起加）
https://devapi.qweather.com    （用和风时才需要）
```

没加也能跑 —— 会静默降级，页面标注数据来源，不会白屏。

心知免费版条款要求数据展示页注明来源，天气页来源区已带「天气数据由心知天气（Seniverse）提供」。

### 7.3 降级策略

```
读缓存(20min) → 命中直接返回
   ↓ 未命中
配了 proxy？→ 走服务端代理（端上不碰 key）
   ↓ 没配 / 代理挂了
定位（失败用农场坐标：湘西龙山 29.45,109.44）
   ↓
seniverse → open-meteo → mock  依次尝试
```

任一步成功就停。失败原因记在 `result.error` 里：

- `mock: true` → 页面标「演示数据」，并把 `error` 显示成一整行黄色提示，说清为什么没取到
- `degraded: true` → 拿到了真数据但不是主源，页面提示「主数据源没连上，已自动切到 X」

这样 key 过期、配额用完之后不会白屏，也不会让人以为数据是准的。

缓存写在 `nh_weather_v2`（换源后从 v1 升到 v2，避免读到旧源的数据），20 分钟有效，省调用量。心知免费版 1000 次/天，按 20 分钟缓存，单机够用。

mock 用日期做种子（`Math.sin(seed)` 那套），**同一天多次打开结果一致**，不会刷一次变一次。

### 7.4 天气码映射

### 7.3 天气码映射

Open-Meteo 用 WMO 码，和风用自己的图标码。统一收敛到 20 个常见天气：

```js
export const WMO = {
  0: { text: '晴', emoji: '☀️', tone: 'gold' },
  2: { text: '多云', emoji: '⛅', tone: 'info' },
  61: { text: '小雨', emoji: '🌦️', tone: 'info' },
  95: { text: '雷阵雨', emoji: '⛈️', tone: 'danger' },
  // …
}
```

和风的码用区间粗分（`qweatherCodeToWmo`），300-399 归雨、400-499 归雪，够展示用。

`tone` 决定页面顶部渐变色：`gold` 晴天橙、`info` 多云蓝、`warn` 雨天深蓝、`danger` 雷暴炭灰。

### 7.5 农事指数

农户关心的不是"几度"，是"今天能不能打药"。所以算四个 0~100 的分数：

| 指数 | 主要扣分项 |
|---|---|
| 打药 | 未来两天降雨概率 ≥70%（-55）、当日降水 ≥10mm（-25）、风速 ≥6m/s（-45）、最高温 ≥35℃（-35）、当前温度 <8℃（-20） |
| 灌溉 | 近三天无雨天数 ×18、最高温 ≥33℃（+15）、当日降水 ≥5mm（-40） |
| 采收 | 降雨概率 ≥60%（-45）、湿度 >90%（-15）、最高温 ≥35℃（-10） |
| 晾晒 | 晴（+40）、最高温 ≥26℃（+15）、湿度 <70%（+15）、有风（+10）、降雨概率 ≥50%（-50） |

分级：≥80 适宜 / ≥60 可以做 / ≥40 不太合适 / <40 别做。

打药这一项刻意给了更狠的扣分。**分数虚高的代价是不对称的** —— 农户照着一个偏高的分打了药，结果下雨冲掉，损失的是真金白银；让他今天别打，最多晚一天。

### 7.6 农事建议

规则引擎，11 条规则，每条都带「为什么」：

| 触发条件 | 建议 |
|---|---|
| 今日降雨概率 ≥70% | 今天有雨，别打药 |
| 未来两天有雨 | 打药赶在雨前，雨前 6 小时以上 |
| 近三天降雨概率 <25% | 盯着浇水，清晨 5-8 点浇 |
| 最高温 ≥33℃ | 避开中午用药，棚内放风 |
| 最低温 ≤5℃ | 盖膜防冻，冻前别浇大水 |
| 风速 ≥6m/s | 喷药会飘移，等风小再打 |
| 湿度 ≥85% 或降雨 ≥60% | 灰霉/霜霉要提前防，雨前打保护性药剂 |
| 温差 ≥10℃ | 适合积累糖分，补一次钾肥 |
| 都没触发 | 天气平稳，按农事日历推进 |

农户信的不是结论，是理由。所以每条都写清"为什么"，而不是只给一句"不宜打药"。

## 9. 自测清单

已跑通的 46 项（`node .work/patch/bundle-farm.js && node .work/patch/farm-test-bundle.cjs`）：

- 地块数量、名额、状态自动判定（满员不再招募）
- 汇总数字与订单数一致（`booked === activeIns`）
- 通过申请：生成订单、名额 +1、申请状态变更、重复调用无效、待确认数下降
- 拒绝申请：状态与原因落盘
- 调价生效、名额不能低于已认养、非法价格被拒
- 暂停/恢复招募，招募中列表随之变化
- 长势推送插入到最前
- 任务勾选/取消
- 配送次数递增
- 大厅联动：`findPlot('mp1')` 能查到、`plotView` 有农场名、大厅含招募中地块、不含满员地块

## 10. 已知限制

1. **认养大厅的分农场筛选不含农户自己的地块**。`plotFilters()` 的农场 chip 来自 `ADOPT_PLOTS`，农户地块 `farmId: 'me'` 没有对应 chip，只在「全部」里出现。接后端后统一从一份地块表出就好。
2. **超额接单只是提示，不拦截**。这是刻意的，但如果后期要做风控，应该在 `acceptApp` 里加一条可配置的硬上限。
3. **天气只做了 7 日预报**，没有逐小时和灾害预警。农业气象预警（霜冻、暴雨橙色）需要接气象局数据源，Open-Meteo 没有国内预警。
